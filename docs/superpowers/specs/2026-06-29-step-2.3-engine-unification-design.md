# Step 2.3 — Engine Unification: Single-Player onto the Deterministic Sim (Design Spec)

**Date:** 2026-06-29
**Status:** Draft for Director review
**Author:** Claude (with Andrew)
**Depends on:** Phase 2.1 (deterministic AI: `decideAI`, `buildAISingleView`, `applyCombatantInput`, `spFrameCounter`, `spRng`), Phase 2.2 (juice + proj-vs-proj in sim, `juice` input boolean, `juiceActive`/`juiceTimer` in hash/capture/restore). Starting golden: `G3` (exact value pinned at end of 2.2 by lead).

---

## 1. Goal

Replace the single-player mesh-based duplicate update loop (~700 lines of `updateGameLogic`) with a unified deterministic path:

1. Gather inputs each fixed tick — player keyboard state → `buildPlayerInput()`; AI decision → `decideAI(buildAISingleView(), ...)`.
2. Feed both into one `simulateNetworkFrame(leftInput, rightInput, dt, buildSimCtx())` per SP tick.
3. Mirror sim state to meshes for rendering.

After this step, SP and MP share ONE simulation engine. Every fix or ability change made in `js/sim.js` applies to both game modes automatically. Doubles stays on the old loop (branch-gated by `isDoublesMode()`) and is out of scope.

---

## 2. The "SP Feel Wins" Principle

Where SP and MP behavior differ, SP's behavior is the correct feel for the game. The sim is updated to match SP, not the other way around. This is a refactor, not a redesign. The acceptance gate for the risky steps is a BEFORE/AFTER single-player playtest run by the lead — not just the oracle hash.

## 3. Paddle-Return Reconciliation

The SP player return (~12662–12694) and AI return (~12741–12771) diverge from the sim's `fireball behavior.onPaddleHit` (index.html ~2126–2143, called from js/sim.js ~256–257/287–288) in seven ways. Every divergence is resolved to SP's value.

### 3.1 Paddle momentum transfer (deterministic paddleVelZ)

SP measures: `paddleVelZ = (paddle.position.z - prevZ) / dt` (index.html ~12270–12277), then applies `proj.velZ += paddleVelZ * 0.4` on hit. The sim has no paddle velocity — `applyNetworkMovement` moves `paddleZ` in a discrete step (js/sim.js ~323–352) and discards the previous position.

Resolution — add `prevPaddleZ: 0` per combatant to sim state:
- In `applyNetworkMovement`, before updating `paddleZ`, record `combatant.prevPaddleZ = combatant.paddleZ`.
- In `onPaddleHit`, derive `paddleVelZ = (combatant.paddleZ - combatant.prevPaddleZ) / dt` and apply the `* 0.4` term.

Both clients execute the same `applyNetworkMovement` step with the same input, so `prevPaddleZ` is identical on both sides — fully deterministic. `prevPaddleZ` must be added to `hashGameState`, `captureGameState`, and `restoreGameState` (see §8).

### 3.2 hitOffset divisor

SP uses `paddleHalfDepth = 1.25` (index.html 11756). Sim uses `0.8` (~2130).

Resolution: set the sim's hit-offset divisor to `1.25`.

### 3.3 Collision hitbox depth

SP effective depth: `1.25 + 0.75 (perspectiveZOffset) = 2.0`. Sim: `0.8 + 0.75 = 1.55`.

Resolution: set the sim's base half-depth from `0.8` to `1.25` (making effective depth `1.25 + 0.75 = 2.0`).

### 3.4 Speed floor — player-side only (preserve SP quirk)

SP applies `Math.max(speed, 10)` on the player/left side only; NOT on the AI/right side.
Sim applies the floor to both sides.

Resolution: match SP's asymmetry — apply the speed floor only when processing the left/player side; remove it from the right/AI side. Document this as a deliberately preserved SP quirk.

### 3.5 Block-mana award

SP: always `+0.5 mana` on a paddle block.
Sim: `+0.5 mana` only if `!isParried`.

Resolution: unconditional `+0.5` (match SP).

### 3.6 `applyCastPushback` on mid-cast block

SP calls `applyCastPushback` when a projectile hits during an active cast (~12693/12769). The sim does not.

Resolution: in `onPaddleHit`, call `D.applyCastPushback(combatant)` via deps when `combatant.casting !== null`.

### 3.7 `resetProjParryState` on opponent-parried ball return

SP calls `resetProjParryState(proj)` when returning a ball that carries an opponent's parry state (~12665/12744). The sim does not.

Resolution: in `onPaddleHit`, when `proj.parryState` indicates the ball was parried by the opponent, call `D.resetProjParryState(proj)` via deps before the return calculation.

### 3.8 FX — render-side only, no sim change

`updateProjectileTier` (scales the ball mesh by `volleyCount`) and `flashShield` (hit-flash on the paddle) are pure presentation effects. They stay on the SP/render side and are NOT ported into the sim. After the engine swap in step C, the SP renderer can still call them using `proj.volleyCount` from the sim state, which the sim keeps current.

## 4. Parry Unification

### 4.1 Current state (two parallel systems)

SP maintains two parallel parry systems:
- Player: `checkParryHits` / `updateParryTimer` — reads player-paddle mesh state.
- AI: `aiCheckParryHits` / `updateAIParryTimer` + `aiCanParry`/`aiParryActive`/`aiParryTimer` (added in 2.1 — `aiCheckParryHits` still reads mesh, noted as deferred in the 2.1 working log).

The sim has: `pvpParryState` (per-side: `active`, `timer`, `canParry`, `successCooldown`, `failCooldown`) + `updatePvPParryTimers` / `tryActivatePvPParry` / `checkPvPParryHitsForSide` (js/sim.js ~377–468), which reads `proj.x/z` — no mesh.

### 4.2 Unified path in 2.3

Both player and AI parry flow through `pvpParryState` in `simulateNetworkFrame`:
- Player presses parry key → `parryCallback` sets `pendingNetInput.parry = true`. `buildPlayerInput()` reads it; `leftInput.parry: true` feeds `tryActivatePvPParry('left')`.
- AI decides to parry → `decideAI` emits `parry: true` → `rightInput.parry: true` feeds `tryActivatePvPParry('right')`.

The 2.1 `aiCheckParryHits` mesh reads are replaced by `checkPvPParryHitsForSide` in the sim, which reads `proj.x/z` only.

### 4.3 Parry constant reconciliation

Before the driver swap (step C), verify the sim's parry constants match SP's values. Expected SP values:
- `parryWindow = 0.5` s
- `parryHitboxExtend = 2.5`
- Success and fail cooldowns — read from SP constants; patch the sim if different.

If constants differ, the sim is patched to match SP (SP feel wins).

### 4.4 Deletions (step D, after step C verified and playtest passes)

Remove from index.html:
- `checkParryHits` function (player parry hit detection).
- `updateParryTimer` function (player parry timer).
- `aiCheckParryHits` function (AI parry hit detection, added in 2.1).
- `updateAIParryTimer` function (AI parry timer, added in 2.1).
- State vars `aiCanParry`, `aiParryActive`, `aiParryTimer` (added in 2.1; replaced by `pvpParryState.right`).
- All call sites in `updateGameLogic` for the above.

## 5. Player Input Canonicalization

### 5.1 How the player acts today

- Movement: `updateGameLogic` reads `keys[]` and mutates `playerPaddle.position.z` directly (~12288/12327–12338).
- Casts: keydown handler calls `startCasting` / `castFrostbolt` / `executeThunderstorm` directly (~3493–3505).
- Parry: `parryCallback` calls the SP parry system directly.
- Juice: Q-key already sets `pendingNetInput.juice = true` (added in 2.2) and calls `activateJuice('player')` directly.

The MP path at ~3453–3461 already does this correctly — it sets `pendingNetInput.*` flags in keydown handlers. The SP path is a parallel, direct-calling duplicate.

### 5.2 Canonical input in 2.3

New function `buildPlayerInput()` runs each SP frame and returns the input struct:

```
{
  moveDir:      (keys['ArrowRight']||keys['d']) ? 1 : (keys['ArrowLeft']||keys['a']) ? -1 : 0,
  parry:        pendingNetInput.parry         (one-shot; cleared after read),
  fireball:     pendingNetInput.fireball      (one-shot),
  frostbolt:    pendingNetInput.frostbolt     (one-shot),
  thunderstorm: pendingNetInput.thunderstorm  (one-shot),
  juice:        pendingNetInput.juice         (one-shot),
}
```

The keydown handlers are simplified so all player actions (casts, parry, juice) set `pendingNetInput.*` flags — the SP-direct calls to `startCasting`/`castFrostbolt`/`executeThunderstorm` and `activateJuice('player')` from keydown are removed, leaving a single unified handler path for both SP and MP.

### 5.3 Retirement of `applyCombatantInput` for singles

The 2.1 `applyCombatantInput` was an intermediate adapter that applied an input struct to a combatant via SP helpers. In 2.3 it is no longer needed for singles — `simulateNetworkFrame` handles `leftInput` and `rightInput` through the sim's own `applyNetworkMovement` and `tryNetworkCast`. It is deleted in step D (unless doubles code still depends on it, in which case it is retained until the doubles unification).

## 6. `runSinglePlayerFrame` Architecture

New function in index.html:

```js
function runSinglePlayerFrame(dt) {
    spFrameCounter++;
    const leftInput  = buildPlayerInput();
    const rightInput = decideAI(buildAISingleView(), spFrameCounter, spRng, AI_PARAMS);
    window.VolleyboltSim.simulateNetworkFrame(leftInput, rightInput, dt, buildSimCtx());
    // Mirror sim state → meshes for rendering
    deps.mirrorPaddleToMesh(combatants.left,  playerPaddle);
    deps.mirrorPaddleToMesh(combatants.right, aiPaddle);
    for (const proj of projectiles) {
        if (proj.mesh) { proj.mesh.position.x = proj.x; proj.mesh.position.z = proj.z; }
    }
}
```

`buildAISingleView()` is updated to read from sim state:
- Projectile positions: `proj.x`, `proj.z` (replacing `proj.mesh.position.x/z`).
- AI paddle: `combatants.right.paddleX`, `combatants.right.paddleZ` (replacing `aiPaddle.position.x/z`).
- Player paddle Z: `combatants.left.paddleZ` (replacing `playerPaddle.position.z`).

The `paddleZ` fields in `combatants.*` are currently stale in SP (only set at init/reset; movement mutates the mesh). In 2.3, `applyNetworkMovement` inside `simulateNetworkFrame` updates `paddleZ` each frame from `moveDir`, so it is always current by the time `buildAISingleView()` is called the following frame. The mesh is then mirrored from sim state, not the other way around.

SP-only render FX (trails, blob shadows, footsteps, castbar, cooldown UI, ice visuals, `spellReady` SFX) remain driven at render-rate or via the `ctx.deps.*` hooks the sim already calls.

### 6.1 Driver branch (the swap point)

The SP accumulator loop at index.html ~13015–13025 (`while gameAccumulator >= FIXED_DT: updateGameLogic(FIXED_DT)`) becomes:

```js
while (gameAccumulator >= FIXED_DT) {
    if (isDoublesMode()) {
        updateGameLogic(FIXED_DT);       // doubles: old loop untouched
    } else {
        runSinglePlayerFrame(FIXED_DT);  // singles: sim-driven
    }
    gameAccumulator -= FIXED_DT;
}
```

Step C adds this branch but does NOT delete the singles body from `updateGameLogic`. The two paths are mutually exclusive. Step D removes the dead singles code.

## 7. What Gets Deleted (Enumerated by Responsibility)

After step C is verified and the SP-feel playtest passes, the following blocks in `updateGameLogic` (and their helpers) are dead for the singles path and are removed in step D:

1. **Player movement** — `keys[]` reads + direct `playerPaddle.position.z` mutation (~12288/12327–12338). Replaced by `applyNetworkMovement` in the sim (fed from `buildPlayerInput().moveDir`).
2. **Player paddle-return** — velZ/velX calculation, mana block, cast pushback, tier update (~12662–12694). Replaced by `fireball.behavior.onPaddleHit` in the sim (now with SP's values from §3).
3. **AI movement adapter** — the 2.1 `applyCombatantInput` call for AI movement in `updateGameLogic`. Replaced by `applyNetworkMovement` in the sim (fed from `decideAI` output).
4. **AI paddle-return** — same structure as player return (~12741–12771). Replaced by `onPaddleHit` in the sim.
5. **Projectile movement** — `proj.x += proj.velX * dt`, `proj.z`, bounce, wall reflection, age increment for the singles path. Replaced by `updateNetworkProjectiles` in the sim.
6. **Projectile-vs-projectile** — SP mesh-based fireball overpower / frostbolt cancel (~12499–12607). Ported to the sim in 2.2; dead here.
7. **Gate/tower collision** — singles path inside `updateGameLogic` for gate checks and tower damage. Replaced by `updateNetworkProjectiles` gate-collision block in the sim.
8. **Juice loops** — SP juice drain/activation in singles `updateGameLogic`. Ported to the sim in 2.2; dead here.
9. **Parry: player** — `checkParryHits` + `updateParryTimer` calls in the singles path. Replaced by `checkPvPParryHitsForSide` + `updatePvPParryTimers` in the sim.
10. **Parry: AI** — `aiCheckParryHits` + `updateAIParryTimer` calls + `aiParryActive`/`aiCanParry`/`aiParryTimer` state vars. Replaced by `pvpParryState.right` in the sim.
11. **Cast processing** — SP `updateCastingState` / `completeCast` calls in the singles path of `updateGameLogic`. Replaced by `tryNetworkCast` in the sim.
12. **`applyCombatantInput` function** — the 2.1 intermediate adapter. Replaced by `buildPlayerInput()` → `simulateNetworkFrame` for both sides.

### 7.1 What stays in `updateGameLogic`

Only doubles-specific code:
- Everything inside `isDoublesMode()` branches.
- Doubles front-paddle collisions (~12774–12909).
- `updateAllDoublesAI` call.

### 7.2 What stays on the render side (not in the sim tick)

- Trail effects, blob shadows, footstep sounds.
- Castbar UI updates.
- Cooldown ring/timer UI.
- Ice ground visuals.
- `spellReady` SFX.
- `flashShield` (paddle hit-flash — called from SP renderer reading sim state).
- `updateProjectileTier` (fireball mesh scale — called from SP renderer reading `proj.volleyCount`).

## 8. Rollback Contract Additions

One addition in 2.3: `prevPaddleZ` per combatant.

### 8.1 hashGameState addition

For each combatant (`left` and `right`), after the existing `paddleZ` mix:
```js
mix(q(c.prevPaddleZ));
```
Adding this changes the oracle hash even when `prevPaddleZ` is zero (FNV-1a is not invariant to additional mix operations). This is the deliberate re-baseline gate for step A.

### 8.2 captureGameState addition

Under `left` and `right` snapshots:
```js
prevPaddleZ: combatants.left ? (combatants.left.prevPaddleZ || 0) : 0,
```
(same for right)

### 8.3 restoreGameState addition

```js
combatants.left.prevPaddleZ  = state.left.prevPaddleZ  || 0;
combatants.right.prevPaddleZ = state.right.prevPaddleZ || 0;
```

### 8.4 Rollback invariant

After step A: `captureGameState()` → mutate `prevPaddleZ` → `restoreGameState()` → `captureGameState()` again must produce the same snapshot as the first. This is the rollback round-trip test in the acceptance criteria.

## 9. Golden Re-baseline

One deliberate re-baseline in 2.3: after step A (paddle-return port + `prevPaddleZ` in hash).

The oracle scripted inputs fire projectiles; some hit paddles under the new, wider hitbox (`2.0` vs `1.55`). The momentum term (`prevPaddleZ`-derived `paddleVelZ`) is now applied on those hits. Combined with `prevPaddleZ` being mixed into the hash (changing the hash structure even at zero value), the oracle fold changes from `G3` (the 2.2 final golden) to a new value `G_2.3`.

`G_2.3` is the single pinned golden for this step. It is not pinned until:
1. Numeric paddle-return correctness tests pass (§10.1).
2. The lead runs a BEFORE/AFTER SP-feel playtest and confirms correct ball-return behavior (§10.2).

There are no further oracle re-baselines in steps B, C, D, or E. The parry constant reconciliation and driver swap do not change what `simulateNetworkFrame` does for the oracle's scripted inputs (the oracle emits no `parry: true` inputs; the driver branch is not in the oracle's code path).

## 10. Verification and Acceptance Criteria

### 10.1 Numeric paddle-return correctness tests

In the browser, during an active match:
- Spawn a fireball at a known position heading toward the left paddle.
- Force `combatants.left.prevPaddleZ = P0` and `combatants.left.paddleZ = P1` for known `P0`, `P1`.
- Run one frame. Verify `proj.velZ` includes the momentum contribution `(P1 - P0) / dt * 0.4`.
- Verify the collision fires when the fireball is at depth `≤ 2.0` from the paddle X (not `1.55`).
- Verify block-mana awards `+0.5` unconditionally (even when `isParried` is true).
- Verify `applyCastPushback` dep is called when `combatant.casting !== null`.
- Verify `resetProjParryState` dep is called for opponent-parried balls.
- Verify the speed floor is NOT applied on the AI/right side when returning a slow ball.

### 10.2 SP-feel playtest (lead-run; required before pinning G_2.3)

Run a full SP singles match before step C. Confirm:
- Ball returns carry the player's paddle-Z momentum (arc follows lateral paddle swipe).
- AI returns feel natural (no unintended speed boost from the removed speed floor on the AI side).
- Parry window and hitbox feel match pre-2.3 SP.

Re-run after step D (deletion). Confirm no behavioral regression.

### 10.3 Oracle correctness

```js
const a = dbg.determinism(180, 12345);
const b = dbg.determinism(180, 12345);
const c = dbg.determinism(180, 999);
// a.fold === b.fold (reproducible)
// a.fold !== c.fold (seed-sensitive)
// a.fold === '<G_2.3>' (pinned only after §10.1 + §10.2 pass)
```

### 10.4 AI oracle unchanged

After ALL steps:
```js
console.assert(dbg.aiDeterminism(50, 42).fold === '2666491c');
```
`decideAI` is not changed in 2.3; `dbg.aiDeterminism` uses scripted views and does not call `buildAISingleView`. The oracle must remain `2666491c`.

### 10.5 Rollback round-trip: prevPaddleZ survives capture/restore

```js

restoreGameState(snap);
console.assert(combatants.left.prevPaddleZ === 3.5, 'FAIL: prevPaddleZ not restored');

```

## 11. Scope Boundaries

**In scope (Step 2.3):**
- `js/sim.js`: `applyNetworkMovement` (prevPaddleZ recording), `fireball behavior.onPaddleHit` (all seven divergences resolved), parry constant reconciliation.
- `index.html`: `buildPlayerInput`, `runSinglePlayerFrame`, updated `buildAISingleView` (sim-state reads replacing mesh reads), updated accumulator branch, `hashGameState`/`captureGameState`/`restoreGameState` (prevPaddleZ), simplified keydown handlers (pendingNetInput only), deletion of the singles duplicate from `updateGameLogic`, deletion of SP-only parry functions and 2.1 AI parry state vars.

**Out of scope (deferred):**
- Doubles AI and `predictZAtX` Math.random.
- `updateGameLogic` doubles path (kept, gated by `isDoublesMode()`).
- New abilities or mechanics.
- Netplay-specific changes (MP already routes through the sim; this step is a SP refactor only).
- The doubles unification (a future step, branch-gated by `isDoublesMode()`).
