## 2. Mechanic: Projectile-vs-Projectile Resolution

Source of truth: `index.html` ~12499–12607.

### 2.1 Frostbolt cancel

When iterating projectiles, for each frostbolt `proj`:

- Skip all other frostbolts (`otherProj.type === 'frostbolt'` → pass through each other).
- Skip any `otherProj` already in the destroy queue.
- Head-on check: opposite X-velocity signs AND moving toward each other (frostbolt going right means `otherProj.x > proj.x`; going left means `otherProj.x < proj.x`).
- Distance check: `sqrt((proj.x - otherProj.x)^2 + (proj.z - otherProj.z)^2) < (proj.hitboxRadius || 0.3) + (otherProj.hitboxRadius || 0.3)`.
- Outcome: both destroyed. No mana award, no juice award.
- After the first collision found for this frostbolt, break (frostbolt is consumed).
- FX: cancel impact flash, "Cancel" combat text, cancel sound → all via `ctx.deps.*`, gated by `isResimulating`.

### 2.2 Fireball overpower (non-frostbolt pairs)

For each non-frostbolt `proj` whose `collisionGraceTime <= 0`:

- Skip `otherProj` that is frostbolt, already in destroy queue, or has `collisionGraceTime > 0`.
- Head-on check: opposite X-velocity signs AND moving toward each other (same directional logic as §2.1).
- Distance check: same formula with `hitboxRadius || 0.3` for both.
- Compute damage: `projDmg = proj.damage !== undefined ? proj.damage : Math.min(2 + proj.volleyCount, 6)`. Same for `otherDmg`.

**Higher damage wins:**
- Winning proj survives; losing proj is destroyed.
- Winner: `volleyCount = Math.min(volleyCount + 1, 4)` (damage tier rises by 1, max 4 → damage 6).
- Winner's owner combatant receives minor juice (`JUICE.CHARGE.minor = 4`).
- FX via deps (impact flash on loser, overpower decal, "Overpowered!" combat text, overpowered sound).
- Break after one collision per `proj`.

**Equal damage — mutual cancel:**
- Both destroyed.
- Both combatants (`combatants.left` and `combatants.right`) receive `+0.5 mana` each, clamped to `D.getMaxMana(side)`.
- Both combatants receive minor juice.
- FX via deps (impact flash, fire decal, "Cancel" combat text, cancel sound).
- Break.

### 2.3 Determinism of iteration order

The SP code iterates with a stable `for…of` over the ordered `projectiles` array. The sim `projectiles` array already maintains insertion order. The proj-vs-proj pass reuses the same `toDestroy` set that `updateNetworkProjectiles` uses, so projectiles consumed in the frostbolt-cancel pass are already excluded from the overpower pass. Both passes run in `proj.id` order — whatever the array order is — which is deterministic because `nextProjectileId` is a synced counter pinned at oracle start.

### 2.4 Where in the sim frame this fires

Inside `updateNetworkProjectiles`, after position/velocity/bounce updates and before the gate collision check. This matches SP ordering: position update → proj-vs-proj → paddle/gate. All in one `toDestroy` set.

## 3. Mechanic: Juice / Ultimate

Source of truth: `index.html` ~1698–1782, ~10493–10494, ~12631, ~12711.

### 3.1 Configuration constants (passed via `ctx.consts.juice`)

```
JUICE_MAX      = 350
JUICE_DURATION = 8      // seconds
JUICE_CHARGE   = { damage: 12, cast: 8, parry: 10, minor: 4 }
               // damage is PER DAMAGE POINT; minor = block/overpower/cancel
```

These constants live in `index.html`'s `JUICE` object today. The sim receives them through `ctx.consts.juice` (injected by `buildSimCtx`). No duplication — `buildSimCtx` reads from the same `JUICE` constant.

### 3.2 Per-combatant sim state (already initialized; must be rollback-safe)

Every combatant object already has `juice: 0`, `juiceActive: false`, `juiceTimer: 0` set at init (~line 1619). This step adds them to `hashGameState`, `captureGameState`, and `restoreGameState` so rollback round-trips them correctly.

### 3.3 `simAddJuice(combatant, amount, juiceConsts)` — pure helper in js/sim.js

```
if juiceActive: no-op (cannot charge while bursting)
combatant.juice = min(juiceConsts.MAX, combatant.juice + amount)
```

No wall-clock, no mesh, no RNG. Same math as SP `addJuice`.

### 3.4 `simActivateJuice(combatant, juiceConsts)` — pure helper in js/sim.js

Guard: `combatant.juice >= juiceConsts.MAX && !combatant.juiceActive`.

On activation:
1. `combatant.juice = juiceConsts.MAX` (stays full; bar drains as timer ticks).
2. `combatant.juiceActive = true`.
3. `combatant.juiceTimer = juiceConsts.DURATION`.
4. Reset all cooldowns once: `for (k in combatant.cooldowns) combatant.cooldowns[k] = 0`.
5. FX (aura spawn, juiceUp sound) → `ctx.deps.onJuiceActivate(combatant)`, gated by `isResimulating`.

Returns `true` on activation, `false` on guard failure.

### 3.5 Juice drain (per frame, in simulateNetworkFrame)

For each combatant with `juiceActive`:
```
combatant.juiceTimer -= dt
frac = max(0, combatant.juiceTimer / juiceConsts.DURATION)
combatant.juice = juiceConsts.MAX * frac
if juiceTimer <= 0:
    juiceActive = false; juiceTimer = 0; juice = 0
    FX: ctx.deps.onJuiceEnd(combatant) gated by isResimulating
```

This runs at the top of the combatant loop in `simulateNetworkFrame`, before any other combatant processing.

### 3.6 Juice activation from input

In `simulateNetworkFrame`, after parry processing:
```
if leftInput.juice && combatants.left: simActivateJuice(combatants.left, consts.juice)
if rightInput.juice && combatants.right: simActivateJuice(combatants.right, consts.juice)
```

### 3.7 Charge hooks

| Event | Where in sim | Hook |
|---|---|---|
| Cast completes | `tryNetworkCast` on successful cast initiation | `simAddJuice(combatant, CHARGE.cast, consts.juice)` |
| Parry success | `D.parryProjectile` dep — already calls SP `addJuice` via the SP function | Flows through the dep IF juice fields exist on the combatant (they do after step A) |
| Proj overpower winner | `resolveNetworkProjVsProj` (new function) | `simAddJuice(ownerCombatant, CHARGE.minor, consts.juice)` |
| Proj mutual cancel | `resolveNetworkProjVsProj` | `simAddJuice` both combatants with `CHARGE.minor` |
| Tower damage | `D.dealDamageToTower` dep — SP function already calls `addJuice(combatant, CHARGE.damage * damage)` | Flows through the dep (same as parry) |

Note on parry and tower-damage hooks: these already fire through the injected SP deps (`D.parryProjectile`, `D.dealDamageToTower`) which internally call `window.addJuice`. This means the hooks are already live for the MP path once juice fields are on the combatant. The sim only needs to add explicit `simAddJuice` calls at the sites it owns directly (cast completion, proj-vs-proj outcomes).

### 3.8 Burst effects

**Burst effect 1 — 6-tier fireball:**
In `fireball` behavior's `onCast` (index.html ABILITY_REGISTRY), after spawning the projectile: if `combatant.juiceActive`, set `proj.volleyCount = 4`, spawn at max speed, scale to full size. The scale update is a presentation dep call (`ctx.deps.updateFireballScale(proj)`) gated by `isResimulating`.

**Burst effect 2 — auto-perfect-parry:**
In `updateNetworkProjectiles`, at the paddle collision block for each side: before checking `pvpParryState.active`, check `combatant.juiceActive`. If true, treat any incoming projectile that hits the paddle zone as an auto-parry — call `D.parryProjectile(proj, side, 0)` directly and add to `toDestroy`. This bypasses `pvpParryState.canParry`, the parry window check, and the parry cooldown entirely. FX (parry sound, no combat log during juice burst) are gated by `isResimulating`.

## 5. Rollback Contract Additions

### 5.1 hashGameState additions

For each of `left` and `right`, add three more `mix()` calls (after existing cooldown mixes):
```js
mix(q(c.juice)); mix(c.juiceActive ? 1 : 0); mix(q(c.juiceTimer));
```

Adding these to the hash changes the golden even when juice fields are zero, because FNV-1a is not invariant to additional mix operations. This is the deliberate re-baseline gate.

### 5.2 captureGameState additions

Under `left` and `right` snapshots, add:
```js
juice: combatants.left.juice || 0,
juiceActive: combatants.left.juiceActive || false,
juiceTimer: combatants.left.juiceTimer || 0,
```
(same for right)

### 5.3 restoreGameState additions

```js
combatants.left.juice = state.left.juice || 0;
combatants.left.juiceActive = state.left.juiceActive || false;
combatants.left.juiceTimer = state.left.juiceTimer || 0;
```
(same for right)

### 5.4 Rollback invariant

After step 2.2: `captureGameState()` → mutate juice fields arbitrarily → `restoreGameState()` → `captureGameState()` again must produce the same snapshot as the first capture. This is the rollback round-trip test in the acceptance criteria.

## 6. Input Shape Change

### 6.1 Add `juice` boolean to all input shapes

`defaultInput()` in index.html returns `{ moveDir: 0, parry: false, fireball: false, frostbolt: false, thunderstorm: false }`. Add `juice: false`.

`pendingNetInput` initialization: add `juice: false`.

`captureLocalInput()`: add `juice: pendingNetInput.juice || false` and reset `pendingNetInput.juice = false` after capture.

The oracle `inp(f, side)` scripted input function: add `juice: false` to the returned object. The scripted inputs do NOT set `juice: true` at any frame — juice is not exercised by the oracle, preserving a clean signal for the re-baseline checks.

### 6.2 Player keydown wiring

The existing keydown handler at ~line 3502 calls `window.activateJuice('player')` directly (SP path). For the MP path, also set `pendingNetInput.juice = true` so the sim receives the activation through its input channel. The SP direct call is fine for now; Step 2.3 will consolidate.

`decideAI` already emits `juice: true` when `self.juice >= MAX_JUICE && !self.juiceActive` (per the 2.1 spec §4.1). `applyCombatantInput` already calls `activateJuice('ai')` when `input.juice`. For the sim path, the `rightInput.juice` flag routes to `simActivateJuice` — same signal, different target.

## 7. FX via Deps Approach

All presentation effects in the new sim code are called through `ctx.deps.*` and are guarded by `!isResimulating` where they must not fire during rollback:

| Effect | Dep call | Guard |
|---|---|---|
| Overpower flash / decal / sound / combat text | `D.onOverpower(midX, midZ, winnerVelX, winnerVelZ)` | `if (!isResimulating)` |
| Cancel flash / decal / sound / combat text | `D.onProjCancel(midX, midZ)` | `if (!isResimulating)` |
| Frostbolt-cancel flash / sound / combat text | `D.onFrostboltCancel(x, z)` | `if (!isResimulating)` |
| Juice activate aura + sound | `D.onJuiceActivate(combatant)` | `if (!isResimulating)` |
| Juice end aura clear | `D.onJuiceEnd(combatant)` | `if (!isResimulating)` |
| Fireball scale update (burst tier) | `D.updateFireballScale(proj)` | `if (!isResimulating)` |

These deps are added to `SIM_DEPS` in index.html, wiring to the existing SP effect functions. The sim itself never calls Babylon, plays audio, or shows combat text directly.

## 8. MP Behavior Change and Golden Re-baseline Implications

### 8.1 New MP behaviors (approved)

After this step, MP matches gain:
- Projectile-vs-projectile resolution (fireballs can overpower or mutually cancel; frostbolts cancel non-frostbolts).
- Juice/ultimate bar charges and activates; burst window gives auto-parry and 6-tier fireballs.
- Juice charge on cast, on parry, on proj-vs-proj outcomes (already flows through deps for tower damage and parry success).

### 8.2 Golden re-baselines (two deliberate points)

**Re-baseline G2** (after Task B — proj-vs-proj + juice in hash):
The oracle scripted inputs fire fireballs on both sides at fixed cadences. Once proj-vs-proj resolution runs in the sim, projectile collisions change `volleyCount` on surviving projectiles and destroy losing ones. This changes every subsequent projectile position in the oracle run, so the folded hash changes from `b1df6797` to a new value `G2`. Juice fields are now in the hash but evaluate to zero (the oracle inputs never set `juice: true`), so the juice-in-hash addition alone does not make `G2` more volatile than the proj-vs-proj change already does.

**Re-baseline G3** (after Task C — juice behavior wired):
The oracle scripted inputs fire fireballs and frostbolts (`f % 37 === 5` for left, `f % 37 === 22` for right, etc.). Each successful cast adds `JUICE.CHARGE.cast = 8` to the caster's juice (the `tryNetworkCast` charge hook). Since juice is now in the hash, non-zero juice values change the folded hash from `G2` to a new value `G3`. The oracle inputs still do not set `juice: true`, so juice never activates during the oracle run — `juiceActive` and `juiceTimer` remain zero. `G3` is the final pinned golden for this step.

### 8.3 Invariant: G2 and G3 must each be verified for correctness BEFORE being pinned

Do not pin `G2` until the overpower/cancel/frostbolt-cancel scenario tests pass. Do not pin `G3` until the juice lifecycle and burst scenario tests pass. The oracle re-baseline is a deliberate gate, not a rubber stamp.

### 9.2 Rollback round-trip: juice is capture/restore safe

```js
// Run mid-match in the browser:
const c = combatants.left;
c.juice = 200; c.juiceActive = true; c.juiceTimer = 3.5;
const snap = captureGameState();
c.juice = 0; c.juiceActive = false; c.juiceTimer = 0;
restoreGameState(snap);
console.assert(combatants.left.juice === 200, 'juice restored');
console.assert(combatants.left.juiceActive === true, 'juiceActive restored');
console.assert(Math.abs(combatants.left.juiceTimer - 3.5) < 0.001, 'juiceTimer restored');
```

### 9.3 Correctness: proj-vs-proj scenario tests

Each test: set up two projectiles with known positions, velocities, volleyCount, type; run one frame of `simulateNetworkFrame`; assert outcomes.

**Scenario A — Fireball overpower (higher dmg wins):**
- Left proj: type='fireball', x=0, z=0, velX=10, volleyCount=3 (dmg=5). Right proj: type='fireball', x=0.4, z=0, velX=-10, volleyCount=0 (dmg=2).
- Expected: right proj destroyed; left proj survives with volleyCount=4 (dmg=6); left combatant gains `JUICE.CHARGE.minor` juice.

**Scenario B — Fireball mutual cancel (equal dmg):**
- Left proj: type='fireball', x=0, z=0, velX=10, volleyCount=0 (dmg=2). Right proj: type='fireball', x=0.4, z=0, velX=-10, volleyCount=0 (dmg=2).
- Expected: both destroyed; both combatants gain +0.5 mana; both combatants gain `JUICE.CHARGE.minor` juice.

**Scenario C — Frostbolt cancels fireball:**
- Left proj: type='frostbolt', x=0, z=0, velX=10. Right proj: type='fireball', x=0.4, z=0, velX=-10.
- Expected: both destroyed. No mana award. No juice award.

**Scenario D — Frostbolt passes frostbolt:**
- Left proj: type='frostbolt', x=0, z=0, velX=10. Right proj: type='frostbolt', x=0.4, z=0, velX=-10.
- Expected: neither destroyed. Both continue on path.

**Scenario E — Grace period blocks collision:**
- Left proj: type='fireball', x=0, z=0, velX=10, collisionGraceTime=0.3. Right proj: type='fireball', x=0.4, z=0, velX=-10, collisionGraceTime=0.
- Expected: no collision (left proj is still in grace). Both survive.

### 9.4 Correctness: juice lifecycle scenario tests

**Scenario F — Juice fills and activates:**
- Set `combatants.left.juice = JUICE.MAX - 1`. Run one frame with `leftInput = {..., fireball: true}` (a cast that triggers the +8 charge hook).
- Expected: after the frame, juice >= JUICE.MAX; the `juice` boolean input flag can now trigger activation.
- Follow-up frame with `leftInput = {..., juice: true}`.
- Expected: `combatants.left.juiceActive === true`, `juiceTimer === JUICE.DURATION`, all cooldowns reset to 0.

**Scenario G — Juice drains over time:**
- Set `juiceActive=true`, `juiceTimer=8`. Simulate 5 frames at dt=1/60.
- Expected: `juiceTimer ≈ 8 - 5/60`; `juice ≈ JUICE.MAX * (juiceTimer/JUICE.DURATION)` (decreasing).
- At `juiceTimer <= 0`: `juiceActive=false`, `juice=0`.

**Scenario H — Auto-parry during burst:**
- Set `combatants.left.juiceActive = true`. Spawn a fireball heading toward the left paddle inside paddle collision zone.
- Run one frame of `simulateNetworkFrame` with `leftInput.parry = false` (no manual parry input).
- Expected: fireball is parried (reflected) despite `parry: false` in input and `pvpParryState.left.canParry` possibly false.

**Scenario I — 6-tier fireball during burst:**
- Set `combatants.left.juiceActive = true`. Run one frame with `leftInput.fireball = true`.
- After the cast resolves: spawned fireball has `volleyCount === 4` (damage tier 6).
